# Task 6：第一阶段质量门审计设计

- 日期：2026-09-03
- 作者：Monkeycode
- 状态：已实施并验证（2026-09-03）
- 上游设计：`docs/superpowers/specs/2026-09-03-easel-inspired-content-workflow-design.md`
- 上游实现：任务 1–5

## 1. 目标

对第一阶段“内容决策与创作质量链”实施最终质量门，确认任务 1–5 的数据兼容、安全边界、来源链、状态流转及构建质量满足既定设计。

Task 6 不增加业务功能、页面、接口或运行时模块。审计发现覆盖缺口时补充必要测试；发现真实缺陷时只做与验收直接相关的最小修复。

## 2. 范围

审计对象限定为：

1. 能力契约与任务上下文；
2. 选题七维评估与人工决策；
3. Hook、平台草稿和版本管理；
4. 人设、质量、发布完整性检查；
5. 人工确认、撤回及今日拍摄衔接。

明确不包含：

- 浏览器自动连接；
- 自动发布；
- 全量 Easel Skill 移植；
- Task 7 或后续阶段功能；
- 与第一阶段验收无关的重构和视觉调整。

## 3. 审计架构

Task 6 复用现有 Node.js 测试、TypeScript 类型检查和 Vite 生产构建，不增加独立审计服务或运行时依赖。质量门分为四层。

### 3.1 数据兼容层

验证旧 JSON 数据启动归一化后获得安全默认值，同时不覆盖已有业务字段：

- 选题评估、决策及工作流默认值；
- 草稿 Hook、版本组、检查结果及人工确认默认值；
- 旧拍摄记录保持可读，不强制套用新确认门禁。

验证 MySQL 集合拆表保存和重新组装后，新增嵌套字段不丢失，重点包括：

- `evaluation`；
- `hooks`、`selected_hook`、`generation_context`；
- `checks`；
- `approval.checks_snapshot`；
- `source_refs`。

### 3.2 安全边界层

验证所有任务 1–5 新增接口和上下文组装满足：

- 只能读取和修改当前 `owner_id` 的资源；
- 越权资源统一表现为不存在，不泄露其他账号信息；
- 选题、草稿、确认和拍摄链路持续保留 `source_refs`；
- `api_configs` 不进入内容上下文；
- API Key、密码、Token、私钥等敏感字段不会写入内容数据或公开响应；
- 构建产物不包含测试用或真实凭据。

审计以确定性测试和受控文本扫描为主，不读取或传输真实生产凭据。

### 3.3 流程状态层

验证完整状态链：

`candidate → evaluated → approved → draft → hooks_ready → content_ready → persona_checked → quality_checked → publish_ready → ready_to_shoot`

重点覆盖：

- 选题未评估不能决策；
- 未确认选题不能通过选题助手进入草稿生成；
- 草稿检查必须按人设、质量、发布顺序执行；
- 阻断结果进入 `needs_revision`；
- 内容或事实状态变化会使下游检查及确认失效；
- 同版本检查和确认请求幂等；
- `force=true` 只用于允许重跑的检查；
- 过期版本返回版本冲突；
- 未确认、已撤回或检查不合格内容不能进入受保护的拍摄/发布状态；
- 撤回保留原确认和检查快照，不删除来源与历史；
- 已发布内容不能撤回确认。

### 3.4 交付质量层

依次运行：

1. 与发现缺口直接相关的专项测试；
2. `npm test`；
3. `npm run typecheck`；
4. `npm run build`；
5. `npm run verify`。

若完整验证失败，先定位根因，再做最小修复；不通过跳过检查或删除测试获得成功结果。

## 4. 数据流

1. 旧 JSON 或 MySQL 集合进入现有归一化/加载边界；
2. 归一化结果经现有 API 和纯函数测试验证；
3. 账号隔离测试以两个明确 owner 构造同 ID 或关联资源；
4. 来源链测试从研究/素材或选题开始，经过草稿、检查、确认和拍摄；
5. 敏感信息测试使用合成哨兵值，检查上下文、序列化状态和构建产物；
6. 状态机测试覆盖成功路径、失败路径、重试和幂等路径；
7. 最终质量门结果写回任务清单及项目文档。

## 5. 错误处理

- 兼容性失败：记录丢失字段和发生阶段，修复归一化或持久化边界。
- 账号越权：视为阻断缺陷，必须修复后重新运行相关测试。
- 来源链断裂：修复最靠近数据丢失点的写入逻辑，不补造来源。
- 敏感信息泄露：视为阻断缺陷，删除泄露路径并增加回归测试；不记录真实凭据值。
- 状态绕过：收紧专用接口或状态前置，不添加客户端兼容绕过。
- 测试不稳定：先确认端口、临时文件和进程生命周期，不以重试掩盖竞态。

## 6. 测试策略

优先扩展现有测试文件，只有现有边界无法清晰承载时才新增聚焦测试文件。

必须提供以下证据：

- JSON 旧数据兼容及归一化幂等；
- MySQL 集合新字段往返保存；
- 新增接口账号隔离；
- 全链路 `source_refs` 保留；
- 内容上下文及公开响应无敏感配置；
- 质量阻断、修改失效、失败重试、版本冲突和幂等行为；
- 选题到人工确认、今日拍摄、发布的端到端路径；
- 全量测试、类型检查和生产构建通过。

## 7. 成功标准

Task 6 完成需同时满足：

1. `tasklist.md` 的 6.1–6.5 均有可复现验证依据；
2. JSON MVP 与 MySQL 模式可读写任务 1–5 新字段；
3. 所有新增接口保持账号隔离、来源引用和密钥边界；
4. 阻断、人工确认、撤回、重试、冲突与幂等行为符合设计；
5. `npm run verify` 全部通过；
6. 范围扫描确认没有浏览器自动连接、自动发布或全量 Skill 移植；
7. 更新任务清单、README、架构、接口、开发指南、任务登记和任务记忆；
8. 不部署、不提交、不推送；完成后停止等待用户验收。
