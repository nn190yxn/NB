## 四、结构性隐患（不算缺陷，但会持续制造缺陷）

1. **前端没有统一的失败出口**：`apiJson` 失败默认安静，所以「有没有处理失败」全靠每处记得写。棘轮只数数量、不判位置。
2. **表单的「忙 / 失败重试 / 防重入」没有统一封装**：抽查到的几处都有，但**以后新加的按钮仍可能漏**，且写不出测试来防。
3. **约定靠人记**：提示词导出形状（P2）、集合登记（已加棘轮）、解析失败的处理方式（已写成规矩：**解析失败绝不能变成一句正面结论**）。
   → 这三条同一根：**凡是「只能靠人记」的地方，都该有一条机器能查的防线**；加不出防线的，说明缺抽象。

## 五、产品体验建议（不是缺陷）

1. **逻辑检查需要一个独立标记行**，并且状态上区分「没检查 / 模型未报 / 报了但被丢 / 有问题」四态——现在四态里有两态显示成同一种「通过」。
2. **质量门的分数与结论文案要一致**：实测 `passed 81` 的同时带着「受众匹配 50、核心观点 55」两条 warning；用户看到 81 分通过，不会去读 warning。
3. **共振 / 逐字稿「一条都关联不上就 502 不落库」**（`RESONANCE_UNLINKED`、`SCRIPT_FLOW_UNLINKED`）虽然诚实，但用户会连点重试；建议文案里直接给「可以做什么」而不是「可以再试一次」。

## 八、补记（2026-09-20）：整套测试的偶发假红，有了形状

本审计原来只记到「全套并行跑时曾 1 次出现 `server/shooting.test.mjs` 整个文件失败（0 个子测试输出、1001ms）」。
同一天又跑到，已能定性定量：

- **数量**：`npm run verify` 7 次里红 3 次（3/7），每次都是**不同的文件**
  （`stage-quality-gate` / `materials-atoms` / `api-settings-api`），形状一致：整个文件失败、0 个子测试、0.8–1.2s。
- **对照**：不走 npm 直接 `node --test` 连跑 10 次全绿；`--test-concurrency=1` 连跑 2 次全绿（41.8s vs 4.5s）。
- **形状来源（探针实验）**：① 测试文件自杀（SIGKILL）的输出形状与失败完全一致；
  ② 模块顶层 `throw` 虽然尾部也是 `'test failed'`，**但会多打印错误和堆栈**——而这些失败一行堆栈都没有。
  → **文件子进程静默死亡，不是端口耗尽报错。**
- **已排除**：内存不够（32GB / 可用 16GB）；服务端崩溃（`logs/crash.log` 当天无记录）。
- **性质**：**假红**，不掩盖真问题；带堆栈的失败才是真失败。
- **拍板（同日补测后）：不治。** 补测：`npm test` 默认并发跑 27 次，红 2 次（≈ 7%）；曾挂过的文件单独连跑 10 次全绿；共 5 个不同文件挂过。
  理由：7% 的基线要证明「限并发真能治」得跑上百次才有统计力，而串行是 41.8s vs 并行 4.5s（代价 8 倍多）——
  拿一个没证据的代价换一个没验证的效果不划算。**变成规矩**：整套跑出「整个文件失败且无子测试」先重跑一次再当失败；带堆栈的失败不用重跑。
  哪天它超过 20% 再治。
