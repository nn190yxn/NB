## 四、结构性隐患（不算缺陷，但会持续制造缺陷）

1. **前端没有统一的失败出口**：`apiJson` 失败默认安静，所以「有没有处理失败」全靠每处记得写。棘轮只数数量、不判位置。
2. **表单的「忙 / 失败重试 / 防重入」没有统一封装**：抽查到的几处都有，但**以后新加的按钮仍可能漏**，且写不出测试来防。
3. **约定靠人记**：提示词导出形状（P2）、集合登记（已加棘轮）、解析失败的处理方式（已写成规矩：**解析失败绝不能变成一句正面结论**）。
   → 这三条同一根：**凡是「只能靠人记」的地方，都该有一条机器能查的防线**；加不出防线的，说明缺抽象。

## 五、产品体验建议（不是缺陷）

1. **逻辑检查需要一个独立标记行**，并且状态上区分「没检查 / 模型未报 / 报了但被丢 / 有问题」四态——现在四态里有两态显示成同一种「通过」。
2. **质量门的分数与结论文案要一致**：实测 `passed 81` 的同时带着「受众匹配 50、核心观点 55」两条 warning；用户看到 81 分通过，不会去读 warning。
3. **共振 / 逐字稿「一条都关联不上就 502 不落库」**（`RESONANCE_UNLINKED`、`SCRIPT_FLOW_UNLINKED`）虽然诚实，但用户会连点重试；建议文案里直接给「可以做什么」而不是「可以再试一次」。

## 六、验证与限制

**本轮读过/跑过什么**

- 全量测试 **421/421**、`npm run typecheck`、`npm run build` 全绿（2026-09-20）。
- 真模型实跑：**10 个入口、14 次模型调用（18 个请求）**（数据用副本、没改配置）。逐条记录在审计报告 25.6 那节。
- 脚本枚举：路由 → 测试的对应关系、前端空捕获计数、`parseXxx` 错误处理、提示词导出形状。

**完全没覆盖的**

- **真实 MySQL 的用户配置重启回读**（本机没有可连的副本库）。
- **桌面端真机**：新安装包没打，注册/注销没在真实桌面应用里走过（代码已修 + 有单测）。
- **断网、超时、额度耗尽、多账号并发**等失败路径的真实演练。
- **其余模型路径**：改稿、去 AI 感、标题灵感、定点替换、合规检测、素材拆解等没跑（本轮只覆盖 10 个入口）。
- **每条路径只跑了 1–2 次**（逻辑检查 6 次）——**只能证明「会变」，给不出命中率**。

**结论力度分级**

- 源码确认 + 测试断言：P1 的「已修复」四行、P2 的提示词形状。
- 真模型实测：25.6 的那些（样本小）。
- **源码确认、未实测**：25.8 的十行结论、「没有素材时是否该硬拦」的判定。
- **启发式**：25.4 的隔离结论——**不能当安全证明**。

**一条未定位的偶发失败**：全套并行跑时曾 1 次出现 `server/shooting.test.mjs` 整个文件失败（0 个子测试输出、耗时恰好 1001ms）；单跑 3/3 通过，随后连跑两次全套（含并发加压）均 421/421。**根因未定位**，与上一轮报告里那句「尚未确认偶发失败根因」同类。

## 七、建议的执行顺序

1. **把「点了按钮没反应 / 失败当空结果」一次做完**（含 `apiJson` 默认失败出口 + 棘轮降到 0）——这一类用户天天遇到，且能一次收口。
2. **逻辑检查四态**（P1 那条）+ 引用闸门长度（P2）——同一个功能，一起改一起验。
3. **两条确定性检查的误判**（编案例词汇表、`第一反应`）——改法明确、可复现、能马上加断言。
4. **25.4 的结构性改造**（数据访问层统一收口所有者过滤）——投入大，但把「靠人记得过滤」变成「默认过滤」。
5. **产品体验建议三条**——低优先。
6. **重跑真模型**（每类入口跑 5–10 次）——要给命中率结论就得加样本；建议在有改动之后跑，而不是现在。
