### 值得留意但**未构成问题**的一处

- 模型调用失败时**静默降级成确定性版本**（`index.mjs:1065`、`1607`）。
  查了 `index.mjs:1064`，模型那条路写了 `provider: result.provider`，
  **结果里带产出方标记，理论上分得清**，所以**不构成「用户分不清」**。
  **若将来要让用户明确知道「这次是降级结果」，需确认兜底那份也带 `provider` 且界面显示它。目前无证据说这是 bug，不作为结论。**

### 【重要】本轮查出的 P1 不是新问题，是**上一轮「按个例修」导致的复发**

这条比具体某个缺口更有价值，**因为它解释了缺口为什么会复发**。

- 上一轮审计（`docs/audits/2026-09-07-user-journey`）的**头号 P1** 原文是：
  > `saveState('api_configs')` 被集合白名单过滤，配置没有进入持久化流程；加密不等于已保存

  建议写的是「**补齐集合注册**与迁移，增加 MySQL 保存→重启读取测试」。
- **上一轮的修法：把 `api_configs` 这一个补进登记清单。没有加任何防住「忘了登记」这一类问题的测试。**
- **结果：后续新加的 `preferences` 又漏了，同一类问题复发**——就是本轮 25.3 查出的那条 P1。
  **它不是新问题，是老问题换个集合再来一次。**

**教训：修「一个实例」和修「一类问题」是两件事。**
上一轮按个例修、验收也按个例过（`api_configs` 能落库了），
**看起来问题解决了，其实只是「这一次」解决了。**

**本轮补上了缺的那一环**：`server/persistence-registry.test.mjs` 静态断言
「每个 `saveState` 用到的集合名都在登记清单里」，**把这类问题从「靠人记得补」变成「忘了就红」**。

**这条教训适用于本报告里的其他发现，也适用于以后的审计**：
修完一个缺口后，**要问一句「这是孤例，还是某一类的一个样本？」**
——后者必须同时补上机器能查的防线，否则下一个样本迟早出现。
**25.7 的 P2 用了同一个手法**（棘轮测试），也是出于这个理由。

## 三、产品体验建议

1. **逻辑检查的呈现可以更清楚（优先级：低）**。通用列表已经渲染 `evidence.message` 和
   `MarkerScope`，**功能是通的**；只是 `evidence.quote` 没被单独拎成一行。
   原文目前**已写在 `message` 里**，所以不是看不到，是没被视觉拎出来。
   共振分析和发布风险把引用渲染成独立的 `原文：「…」` 一行，扫起来更快。**属排版优化。**
2. **「没查」和「查过没问题」在界面上要一眼分得开**。本次已把「没查」的说明补进
   `suggestions`，但两者**状态都显示「通过」**。若用户会据此判断稿子是否安全，
   建议让状态本身区分（例如「未检查」）。
3. **逻辑检查的测试厚度弱于老三项**。`logic` 只有 1 个测试文件，`persona`/`quality` 各 8 个、
   `publish` 5 个。符合预期（它本次新增），但**边角情况上的保护确实更薄**，后续加固从这里入手。

## 四、验证与限制

**这一节请务必读完再看结论。**

- **只用 JSON 模式验证，未用 MySQL 模式**。本机 `3306` 未监听、没有 `.env` 的 `PROJECT_DB_*`，
  **没有可连的副本库**。所以 **P1 那条是「源码确认」，不是实测**。
  **不许拿生产库来补这个验证。**
- **25.4 所有者隔离**：**结论是启发式得出的，不是证明**，三条限制必须一起读：
  1. **判定靠关键词**。一个路由可能某处用了 `owned(`，却在另一处泄漏——**关键词在，不代表每一处访问都过滤了**。
  2. **只覆盖 `state.*` 的直接访问**。经函数间接访问的（把 owner 传进辅助函数那种）不在这套判定里。
  3. **只查了 `server/index.mjs`**。
  → **要更硬的保证，不该靠审计逐条看**：应在数据访问层统一收口，让所有读都强制经过带所有者参数的取数函数，**这样这类问题结构性地不可能发生**。
  → 前两次尝试（按行匹配、按「路由行到下一路由行」切块）**都失败**：前者 31 条待查几乎全是噪音；后者只认出 1 条草稿路由，**识别漏了，「无问题」就什么也证明不了**。第三次换成大括号配对后识别到 24 条，**这才有可信度**。
- **25.3 的 P1 是「源码确认」，不是实测**（虽已按 P1 修复，但这条限制依然成立；不许拿生产库补验证）。
- **本轮有三次「假发现」，都是同一个毛病：凭记忆/凭类型反推，不查代码。** 如实记下：
  1. 计划原 22.1 写「逻辑检查在界面上渲染不出来」——**读渲染代码后发现是错的**，通用列表本来就渲染。
  2. 25.2 脚本里**编了一个不存在的接口名**（`idea-groups`），跑出「没有测试提到」，像个 P1 缺口；回代码一搜根本没这个路由。
  3. 25.3 第一版只抓了一个登记清单，跑出「10 个集合漏掉」，含 `profile`/`positioning`/`strategy`；实际有三个清单，**10 个里 9 个是假的**。
     **留下的规矩：找清单必须把源码里所有登记点找齐；找到「重大发现」时先回头问自己漏了什么。**
- **测试跑绿不等于测到了东西**。24.1 的第一版路由测试**是空过的**——`evidence` 实际为空数组，
  「每条必须是对象」的循环压根没执行，测试却绿。加诊断打印实跑内容才发现。
  修的时候还写过一个**恒真的假断言**（`length === 0 || length > 0`），当场删掉。
- **未覆盖的**：`server/` 下除 `index.mjs` 外其他文件的 `catch`；**前端 `src/main.tsx` 的失败路径**（界面拿不到数据时显示什么）；
  接口的错误分支（429/422/502）有没有测试；前端动作有没有对应测试。
