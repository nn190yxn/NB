### 25.5 前端失败路径（本轮补查，计划里点名的那一块）

**查法**：列出 `src/main.tsx` 里所有空捕获（`.catch(() => undefined)`、`.catch(() => {})`）与裸 `catch`，
**逐处回读它后面的渲染代码**，判断「失败之后用户看到什么」（不靠函数名猜）。
数字是脚本数出来的：`src/main.tsx` 32 处 + `desktop/main.mjs` 1 处 = 33 处。
（重列清单的写法：在 `src/`、`desktop/` 里搜 `\.catch\(\s*\(\s*\)\s*=>\s*(undefined|\{\s*\})`。）
行号会随编辑漂移，所以下面按「用户看到什么」分类点名，不按行号。

| 哪些位置（按用户看到什么分类） | 用户点了什么 | 失败后用户看到什么 | 该不该报 |
|---|---|---|---|
| `runDraftCheck`（已修） | 开始检查 / 重新检查 | 原来什么都不说，检查项停在原处 | **该报（P1，本轮已修）** |
| 草稿首次加载 | 进「内容创作」 | 「还没有草稿…」空状态——**用户以为稿子没了** | **该报（P1）** |
| 创作面板的可用选题 / 方法 / 金句 / 经历下拉 | 进「内容创作」 | 下拉里空——以为没有可用的已确认选题 | 该报（P2） |

| 同步冲突检查 | 进工作台 | 冲突横幅不出现——**以为没有冲突** | 该报（P2） |
| 内容日历 | 进「内容日历」 | 空日历（代码里就是 `catch(() => setEntries([]))`，改一行的事） | 该报（P2） |
| 定稿审批 / 撤回、档案变更审核 | 点「定稿」「撤回」「通过审核」「拒绝」 | 什么都不说，按钮恢复原样 | 该报（P2） |
| 去 AI 味、复制变体、归档、查看历史、恢复版本、拍摄进度保存、删除记忆 | 点对应按钮 | 什么都不说 | 该报（P2） |
| `apiJson` 自已的响应体解析、看板计数、未读徐标、首次引导、后台预取 | 后台自动（用户没点） | 数字/徐标/列表显示为空或 0 | 弱信号，可接受但要登记 |

**一条模式**：「用户主动点了按钮」的那一批全部无声；「后台读数据」的那一批，
**失败与空结果在界面上是同一种样子**。后者正是上一轮报过的「接口失败被当成空结果」——
**上一轮修的是当时报的那几处，这一类没有机器防线，所以还在。**

**已修（本轮）**：`runDraftCheck` 一处（计划点名的那处），并加了一道棘轮测试（下一条）。
**未修（已登记，等并回 21-24）**：其余「点了按钮没反应」与「失败当空结果」的那些。
**建议的结构性做法**：给 `apiJson` 加一个全局失败出口（默认上报，需要安静的调用点显式 `opt out`），
**把这一类从「靠每处记得 catch」变成「默认会响」**。这是改造，不在本轮做。

**本轮新加的防线**：`server/frontend-silent-catch.test.mjs`——空捕获的数量棘轮。
不强制修完（那要动 30+ 处），只把「现在允许有多少」钉住：
多一个就红，少一个也红（不把数字往下调，就不能真的修完一处）。
**它管不住的**：位置合不合理、吞掉的是不是用户能看见的事——只保证数量不无声增长。

### 25.7 解析函数的错误处理约定（本轮补完）

**查法**：枚举 `server/` 下的 `parseXxx`，逐个回读实现**和调用点**——少了调用点这一步，结论会反过来。

| 模块 · 函数 | 解析不出来时 | 用户在界面上看到什么 | 该不该改 |
|---|---|---|---|
| `claims.parseClaims`、`deconstruct.parseDeconstruction`、`content-form.parseFormJudgement`、`positioning-generation.parsePositioning/parseTopics` | 抛错 | 502 + 具体错误文案 | 不该 |
| `draft-writing.parseReviseBody/parseDraftBodies` | 抛错 | 502 | 不该 |
| `draft-writing.parseReplacePairs`（定点替换） | 返回空数组 | 调用点把它翻成 `502 REPLACE_EMPTY`，文案写明「要么原句对不上，要么改完更短」 | 不该（翻译做得对） |
| `ideas.parseTitleIdeas/parseHookIdeas` | 返回空数组 | 调用点翻成 `502 IDEAS_UNTRACEABLE`，文案点名「公式编号不存在或方法名不认识」 | 不该（翻译做得对） |
| **`draft-logic.parseLogicFindings`** | 原为返回空数组 | **`status: 'passed'` → 界面「已通过」** | **该改（就是本节第一条 P1，本轮已改）** |

**为什么另两处返回空数组不算问题**：它们的调用点都把「空」翻译成了一句说人话的 502，
**用户不会被骗**；而 `draft-logic` 那处的调用点把「空」当成了「没毛病」。
→ **真正的规矩不是「解析失败必须抛错」，而是「解析失败绝不能变成一句正面结论」**。
下次写新模块时，这句才是判断依据——返回空数组可以，前提是调用点必须把它说成失败。

### 值得留意但**未构成问题**的一处

  查了 `index.mjs:1064`，模型那条路写了 `provider: result.provider`，

### 【重要】本轮查出的 P1 不是新问题，是**上一轮「按个例修」导致的复发**

这条比具体某个缺口更有价值，**因为它解释了缺口为什么会复发**。

- 上一轮审计（`docs/audits/2026-09-07-user-journey`）的**头号 P1** 原文是：
  > `saveState('api_configs')` 被集合白名单过滤，配置没有进入持久化流程；加密不等于已保存

  建议写的是「**补齐集合注册**与迁移，增加 MySQL 保存→重启读取测试」。
- **上一轮的修法：把 `api_configs` 这一个补进登记清单。没有加任何防住「忘了登记」这一类问题的测试。**
- **结果：后续新加的 `preferences` 又漏了，同一类问题复发**——就是本轮 25.3 查出的那条 P1。
  **它不是新问题，是老问题换个集合再来一次。**

**教训：修「一个实例」和修「一类问题」是两件事。**
上一轮按个例修、验收也按个例过（`api_configs` 能落库了），
**看起来问题解决了，其实只是「这一次」解决了。**

**本轮补上了缺的那一环**：`server/persistence-registry.test.mjs` 静态断言
「每个 `saveState` 用到的集合名都在登记清单里」，**把这类问题从「靠人记得补」变成「忘了就红」**。

**这条教训适用于本报告里的其他发现，也适用于以后的审计**：
修完一个缺口后，**要问一句「这是孤例，还是某一类的一个样本？」**
——后者必须同时补上机器能查的防线，否则下一个样本迟早出现。
**25.7 的 P2 用了同一个手法**（棘轮测试），也是出于这个理由。

## 三、产品体验建议

1. **逻辑检查的呈现可以更清楚（优先级：低）**。通用列表已经渲染 `evidence.message` 和
   `MarkerScope`，**功能是通的**；只是 `evidence.quote` 没被单独拎成一行。
   原文目前**已写在 `message` 里**，所以不是看不到，是没被视觉拎出来。
   共振分析和发布风险把引用渲染成独立的 `原文：「…」` 一行，扫起来更快。**属排版优化。**
2. **「没查」和「查过没问题」在界面上要一眼分得开**。本次已把「没查」的说明补进
   `suggestions`，但两者**状态都显示「通过」**。若用户会据此判断稿子是否安全，
   建议让状态本身区分（例如「未检查」）。
3. **逻辑检查的测试厚度弱于老三项**。`logic` 只有 1 个测试文件，`persona`/`quality` 各 8 个、
   `publish` 5 个。符合预期（它本次新增），但**边角情况上的保护确实更薄**，后续加固从这里入手。

## 四、验证与限制

**这一节请务必读完再看结论。**

- **只用 JSON 模式验证，未用 MySQL 模式**。本机 `3306` 未监听、没有 `.env` 的 `PROJECT_DB_*`，
  **没有可连的副本库**。所以 **P1 那条是「源码确认」，不是实测**。
  **不许拿生产库来补这个验证。**
- **25.4 所有者隔离**：**结论是启发式得出的，不是证明**，三条限制必须一起读：
  1. **判定靠关键词**。一个路由可能某处用了 `owned(`，却在另一处泄漏——**关键词在，不代表每一处访问都过滤了**。
  2. **只覆盖 `state.*` 的直接访问**。经函数间接访问的（把 owner 传进辅助函数那种）不在这套判定里。
  3. **只查了 `server/index.mjs`**。
  → **要更硬的保证，不该靠审计逐条看**：应在数据访问层统一收口，让所有读都强制经过带所有者参数的取数函数，**这样这类问题结构性地不可能发生**。
  → 前两次尝试（按行匹配、按「路由行到下一路由行」切块）**都失败**：前者 31 条待查几乎全是噪音；后者只认出 1 条草稿路由，**识别漏了，「无问题」就什么也证明不了**。第三次换成大括号配对后识别到 24 条，**这才有可信度**。
- **25.3 的 P1 是「源码确认」，不是实测**（虽已按 P1 修复，但这条限制依然成立；不许拿生产库补验证）。
- **本轮有四次「假发现」，都是同一个毛病：拿二手结论当一手事实，跳过「回代码看一眼」。** 如实记下：
  1. 计划原 22.1 写「逻辑检查在界面上渲染不出来」——**读渲染代码后发现是错的**，通用列表本来就渲染。（凭类型反推）
  2. 25.2 脚本里**编了一个不存在的接口名**（`idea-groups`），跑出「没有测试提到」，像个 P1 缺口；回代码一搜根本没这个路由。（没验就信）
  3. 25.3 第一版只抓了一个登记清单，跑出「10 个集合漏掉」，含 `profile`/`positioning`/`strategy`；实际有三个清单，**10 个里 9 个是假的**。（漏找登记点）
  4. **25.1 报了一个不存在的 P2**：说三份报告的 `evidence` 形状没人测。错在我自己写的字段抽取脚本**会把嵌套类型拍平**——`main.tsx:831` 的 `DraftResonanceReport` 里 `evidence` 是 `dimensions[]` **内部**的字符串字段，报告顶层根本没这个字段。**该 P2 已撤回**（`3635009`）。
     **这一条比前三条更该记**：前三次是凭类型/凭记忆，**这次是信了一个我自己写的、但我没验过的解析结果**。
     **留下的规矩：脚本抽出来的结构，至少要挑一处回原文件核对——尤其是它支持的结论很重的时候。**
- **测试跑绿不等于测到了东西**。24.1 的第一版路由测试**是空过的**——`evidence` 实际为空数组，
  「每条必须是对象」的循环压根没执行，测试却绿。加诊断打印实跑内容才发现。
  修的时候还写过一个**恒真的假断言**（`length === 0 || length > 0`），当场删掉。

**2026-09-20 追加的证据与限制**（这一轮的两条 P1）：

- **是实测，不是源码推断**：两条都走真实 HTTP 服务器进程验证（模拟模型，`server/logic-check-route.test.mjs`
  与 `server/logic-check-api.test.mjs`）。假阴性的证据是修复前的实测返回值：
  **`200` + `checks.logic.status: 'passed'`**（断言输出 `200 !== 502`）。
- **仍然不是真模型实测**：模拟模型是**我们写死的、故意坏掉的输出**（`invalid` 模式回 `invalid JSON`）。
  它证明了「模型输出坏了会怎么走」，**没有证明真实模型多常回坏输出**——后者是 25.6 的未做项。

- **本轮动了一条旧测试的切法**：`server/web-assets.test.mjs` 的「覆盖性动作必须受脏状态保护」，
  原来只切声明那一行；`runDraftCheck` 改多行后保护语句落到第二行，测试会误报。

  **记一笔的原因**：「改测试让它变绿」是危险动作，这次成立的依据是——**断言的意图没变，变的只是取文本的切法**。
- **未覆盖的**：真模型端到端（25.6 只在 2026-09-19 跑过逻辑检查这一条，见上表）；MySQL 模式；浏览器里真的点一遍（本机没装无头浏览器，也没有可用的服务进程）。
  （**2026-09-20 更新**：本轮改的是「模型输出不可解析时怎么办」这条分支，真模型在那个 2026-09-19 的实测里返回的是**干净 JSON**，
  所以这条改动在真模型上大概率中性偏正；但那是**修前**的实测，**修后没重跑真模型**。）
