## 2026-09-14 · 受众判据的根因，以及更正我上一轮的一个错误结论

### 先更正上一轮说错的话

上一轮我写「`audience_weak`、`point_weak` 也是 32/32 全中」。**`point_weak` 那句是错的**，原因是我自己的标定脚本写错了：`profile_by_user` 是按用户 id 索引的**对象**，我却写成 `profile_by_user?.find?.(...)` —— `find` 在对象上是 undefined，于是静默回退到顶层种子档案，拿别人的档案去比他的草稿。

用**他真实的档案**重测（32 条真实草稿，正文里出现档案原话才算命中）：

| 判据 | 整句命中 | 结论 |
| --- | --- | --- |
| 受众 `audience_weak` | 1/32 | 确实等于永远不过 |
| 观点支柱 `point_weak` | 25/32 | **能正常分辨**，上轮结论作废 |

上一轮服务器实测里草稿 #37 的 `core_point` 本来就是 100，这里也印证了同一件事。

### 受众判据的根因（不是判据写错，是数据形状不对）

判据靠「正文里出现档案里的原话」。他档案里 `pillars` 是 5-6 字短语（「素材原子化」「定位先于内容」）→ 25/32 命中，正常；但 `audiences` 是 **17 字整句**（「想做个人IP却每天从零开始的创业者」）→ 正文永远不可能原样出现这句 → 1/32。

整句是哪来的：`server/index.mjs` 里生成定位建议的提示词**对这三个字段没有任何格式约束**，模型就按自己的理解写了整句。

### 改了什么

1. **定位生成的提示词**（`server/index.mjs`）要求 `audiences`、`problems`、`pillars` 用 2-8 字短词或短语，并说明原因：质量门靠正文出现这些原话判断贴合度，写长了永远匹配不上。
2. **质量门把原因直接写在建议里**（`server/draft-checks.mjs`）：档案值超过 12 字时，提示改成「档案里的「…」有 17 字，正文不会原样出现这句，所以这条会一直命中；把它改成 2-8 字短词（例如「个人IP创业者」），或确认正文确实对上了之后忽略」。原来的提示是「明确读者是谁以及正在解决什么问题」——让人去改正文，而真正要改的是档案。

### 为什么不干脆把判据放宽

试过按滑窗匹配（正文里出现档案原话的任意 N 字片段就算命中），实测：

| 粒度 | 受众命中 | 支柱命中 |
| --- | --- | --- |
| 整句（现状） | 1/32 | 25/32 |
| 5 字窗 | 16/32 | 25/32 |
| 4 字窗 | 28/32 | 29/32 |
| 3 字窗 | 28/32 | 32/32 |
| 2 字窗 | 32/32 | 32/32 |

放宽到 4 字窗就接近全中，判别力等于消失（一个只会说「都对」的检查比没有检查更糟）。所以选择**保留严格判据 + 把根因说出来 + 约束上游数据形状**，而不是改成一个永远通过的检查。

### 验证

201/201 测试（新增 1 项：整句受众要给「写太长」提示、换成短词且正文真出现后不再命中、全部 ≤12 字时不给该提示），`tsc --noEmit` 通过。

### 需要他定的一件事

他档案里两条 17 字受众还没改（`fillProfile` 只在字段为空时写入，重新生成定位不会覆盖已有值）。要改的话把「想做个人IP却每天从零开始的创业者」改成「个人IP创业者」这类短词即可，我没动他的档案数据。

## 2026-09-14 · 编造的客户案例：12 条草稿 12 条都在编

### 问题（并把上一轮的错误结论纠正掉）

上一轮我把 #40 里的「家政收纳」内容归因为「素材库里的对标样本被误用」——**这个结论是错的**。查证过程：

- 素材库 33 条全是「对标dbs·金句 / 句式 / 洞察」，对标样本 0 条，逐条扫过没有任何家政、收纳、打扫相关内容；
- 全文检索 `server/data.json`：家政 / 打扫 / 收纳只出现在草稿 #37–#40 里，素材、研究库、选题都没有。

所以那不是素材污染，是**模型自己编的案例**。而且不止一条：**12 条草稿里 10 条都写了「具体客户案例」**——

- #39 / #40：「上个月，一位做本地家政的老板，提炼出一个核心观点：干净不是扫出来的，是收纳出来的」；
- #41–#44：「我有个客户，换了5个定位，最后用「本地老板IP顾问」这个定位，3个月涨粉2万」；
- #45–#48：「某本地老板转型三个月，因为定位模糊，流量归零」。

根因是提示词自相矛盾：一条要求「正文用具体经历、场景、数字或证据支撑」，另一条禁止「编造成绩、客户或数据」。而他的素材库里**只有对标样本、没有一条己方素材**，模型为了满足前者只能编后者。对一个靠真实案例立信的 IP 顾问，这是最危险的一类内容错误。

### 改动

- `server/draft-writing.mjs` 把「不编造」这条改写成可执行的出路：「具体支撑」只能用简报里的素材或确知的真实经历，简报里没有案例时改用通用现象或判断说明，**宁可少一个案例也不编造**。不是再堆一条禁令，而是把两条打架的规则接上。
- `server/draft-checks.mjs` 新增 `case_claim` 检查（warning）：把正文里的「案例人物」（一位做家政的老板 / 我有个客户 / 某本地老板）与「结果数字」（涨粉 / 翻倍 / 归零 / 3个月涨粉2万）挑出来让人确认。
- 刻意收窄精度：人物词必须紧跟数量词，所以「一个反问：你确定你的客户…」不算案例；「上周把选题拆成三条」这类时间描述也不算。

### 验证

- 196→197 项测试全绿（新增 1 项：三类真案例命中、三类通用表述不误伤），`tsc --noEmit`、生产构建通过。
- 真实草稿逐条扫：**10 条命中且证据是原文原话**（#39–#48），#37 / #38 未命中（那两条只提到「家政老板」这个品类，没编具体客户）——符合预期。

## 2026-09-14 · 堵住二进制文件静默入库（素材库乱码）

### 问题

浏览器上传走 `FileReader.readAsText`，PDF/DOCX/XLSX 这类二进制文件到了服务端就是一堆乱码文本；而 `parseMaterialContent` 对 `pdf`/`word` 格式**只要来的是文本就标记 `status: ready` 入库**，从不判断「是否真的解析出了正文」。结果是乱码被当成正常素材存下来，且 `error` 为 `null`，看不出有问题。

（`excel` 格式同一类问题：乱码里大概率含逗号，会被 CSV 分支当成 `ready`。）

### 改动

- `server/validation.mjs`：新增 `binaryUploadError()`，在 `parseMaterialContent` 入口对所有文本类格式统一拦截，判据用实测过的信号——压缩包魔数（PK 紧跟 0x03 0x04）、PDF 文件头、NUL 字节、UTF-8 解码乱码字符占比。命中时返回 `status: failed` 并给出可执行的原因（「请另存为 .txt 或 .md 后重新上传」），`content` 仍保留原文便于排查与重试。
- `src/main.tsx`：上传前先按扩展名拦一层，直接给提示，不再产生垃圾素材记录。
- 浏览器文本解码出少量坏字符不会被误伤：实测正常中文正文乱码占比 0%，含 3 个坏字节的文本 0.7%，而真实二进制 42%–44%，阈值取 5% 有足够余量。

### 验证

- 192→193 项测试全绿（新增 2 项：二进制拦截、正常文本不误伤），`tsc --noEmit`、生产构建通过。
- 重启本地 API 后用真实接口上传四种文件核对：假 DOCX、假 XLSX、假 PDF 全部 `status: failed` 并给出对应原因，正常 Markdown 仍为 `ready`。
- 顺带扫描了他素材库里已有的素材：37 条中带二进制乱码特征的只有本次验证产生的 3 条（验证后已软删除），**他原有素材没有被这个 bug 污染**。

### 未做

- 没有引入文档解析依赖，所以 DOCX/PDF 仍然只支持「先另存为文本」。要真正支持二进制解析，需要新增依赖（mammoth/PDF 解析库），这是独立决定，没有擅自加。
- 受浏览器上传限制，PDF/DOCX 的真实解析仍走桌面同步通道（`parseSyncJob` 有 buffer 路径，DOCX 会诚实报「需要文档解析依赖」）。
