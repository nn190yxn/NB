## 2026-09-18 · 定点替换上线，句子级判据补 7 条

用户实测反馈：整篇重写这条路在去 AI 味上会死循环——模型一重写就把句子换回同样的腔调，两次机会用完，稿子卡在「未改库」。所以补一条不重写整篇的通道。

**定点替换（按句换，其余一字不动）**

- `POST /api/drafts/:id/replacements`：模型只回 `{"pairs":[{"old":"原文这句","new":"改成这句"}]}`，服务端校验 old 在正文里唯一存在、new 不是原样、不越改越短；不合规的条目退回并说明原因，预览不改库。
- 草稿页「修改意见」旁新增「定位替换」：逐条对照、可勾选，替换直接落进正文（走已有的保存流程，version+1），并回报换完还剩几处命中。
- 用户确认过的替换不做拦停——拦停只拦模型自动产出，人比规则大。

**句子级判据补 7 条**（全部接入 writingIssues 拦停 / checkQuality 留证据 / checkRewriteHints 给指令）

- `triple_list` 凑数三连：三连里至少两项是抽象词才拦，「选题、拍摄、剪辑」这种具体清单不拦
- `golden_tail` 段尾金句收束（其实…才是…）
- `generic_ending` 万能结尾（未来可期、拭目以待、迈出了重要一步）
- `ing_tail` 象征着 / 反映了 / 体现了
- `avoid_copula` 作为…的角色、发挥了…作用、标志着
- `fake_rebuttal` 有人可能会说、难道不是吗
- `connector_abuse` 首先/其次/此外/综上所述等书面连接词出现两种以上；单次「首先」不拦

## 2026-09-18 · 去 AI 味三条判据上线（命中即重写）

## 2026-09-14 · 复盘的「往常」：模型路径拿不到基线，而且它的结论进不了基线池

### 问题（两处互相加剧）

**一、模型路径的复盘不记 `rate`。** 确定性复盘会算互动率并写入 `retrospect.rate`；走大模型那条分支只存 verdict/summary/lessons/drivers，没有 rate。而「和往常比」的基线完全依赖它：

```js
const peers = ...filter(item => Number.isFinite(Number(item.retrospect?.rate)))
```

`Number(undefined)` 是 NaN → **所有走模型的复盘都进不了 peers**。他配着 Key、默认走模型，所以基线池实际是空的：后面每条复盘都只能靠绝对口径（互动率 ≥5% 才算好）判断。

**二、模型被要求判「优于/低于往常」，但请求里没有任何历史数据。** 用户消息只传 title / platform / metrics / body —— 没有基线，也没有同类内容的历史。模型只能凭空给一个 verdict，而这条 verdict 会被写进「AI 记忆」的 feedback，再注入之后的选题与草稿生成。也就是说：一个没有依据的「优于往常」会变成一条喂给未来内容的假经验。

### 改动

1. `retrospectDeterministic` 的结果里带上 `peer_average` 与 `peer_count`（基线只算一次，接口层复用）。
2. 接口层先算一次确定性结果 `deterministic`，模型路径：
   - 把 `baseline: { rate, peer_average, peer_count }` 传进请求；
   - 存下的复盘补上 `rate` / `peer_average` / `peer_count`（于是模型路径的复盘也能当别人的基线）；
   - 系统提示词给出判定口径：有基线就按「高于基线 20% 记 winner、低于 20% 记 underperformed」，**没有基线时不允许凭空说「优于往常」**，退到绝对口径（互动率 ≥5% 记 winner），与确定性路径一致。

### 验证

204/204 测试。新增断言：

- 纯函数：无历史时 `peer_count 0 / peer_average null`；两条历史（1%/3%）→ `peer_count 2 / peer_average 0.02`；同一份 3% 的数据，**有基线判 winner（比 2% 高 50%）、无基线判 ok（3% < 5%）** —— 证明基线确实参与了判定
- 接口层：走模型的复盘必须记下 `rate`（把新写法临时换回旧写法确认会红：`实际 undefined`），且第一条复盘成为第二条的基线（`peer_count 1`、`peer_average` 等于第一条的 rate）

### 没验证的

提示词里那条判定口径的实际效果 —— 需要一次真实生成，会花他自己的模型额度，等他同意。

## 2026-09-14 · 提词器的「速度」滑块是死的

### 问题

拍摄页面的提词器有三个控件：开始滚动 / 字号 / 速度。实测发现：

- **字号**有效（`style={{ fontSize }}`）✓
- **速度滑块完全无效**：`scrollSpeed` 只写进 state、localStorage 和拍摄记录，从头到尾没有参与渲染，全项目没有任何一行自动滚动逻辑
- **开始滚动**只是给容器加了 `is-playing`，而那条 CSS 是 `transform: translateY(-11.5px)` —— 文字往上挪 11.5 像素就完事了，看起来像"滚了一下"，其实没滚动

也就是说：拍摄时提词器不会自己往下走，只能手动滚。

### 改动

1. `src/shooting-utils.ts` 加 `teleprompterStep(speed, deltaMs)`：1-8 档对应每秒 3-24 像素（按口播语速校准：250 字口播约 60-90 秒、一屏脚本约 400 像素，档位 3-5 大致贴合）。用真实帧间隔算，60Hz 与 120Hz 屏幕速度一致；单帧最多按 250ms 算，避免切回标签页时一下子跳到底。
2. `src/main.tsx`：提词器容器挂 ref，`playing` 时用 `requestAnimationFrame` 递增 `scrollTop`。暂停从当前位置继续；滚到底自动停；**已经到底时再点开始会先回到顶部**（否则一按就立刻到底停住，成死路）。
3. `src/styles.css`：删掉那句假滚动的 `translateY(-11.5px)`，换成滚动中的左侧强调色标识；顺手清掉只为它服务的 `transition: transform`。

### 验证

203/203 测试（新增 `server/teleprompter.test.mjs`：档位单调、1-8 档映射、60Hz 与 120Hz 帧率无关、3 档 70 秒滚 630 像素够走完一屏、越界档位夹紧、单帧上限、负值与 NaN 不产生 NaN）、`tsc --noEmit`、生产构建通过。

**没验证的**：浏览器里的实际滚动效果。项目里没有 jsdom / playwright（jsdom 也不做布局，测 `scrollHeight` 没有意义），所以这一层只有代码审查 + 类型 + 构建保证。要真机确认，需要在浏览器里打开拍摄页按一次「开始滚动」。

### 过程中的一个失误

第一次插入滚动 effect 时，`/api/shooting/today` 这个字符串在首页组件里也出现一次，我匹配到了第一处，效果钩子插进了错误的组件作用域（`tsc` 立刻报 7 个 `Cannot find name`）。已按 `scriptRef` 之后的第一处重新定位，类型检查通过。

## 2026-09-14 · 堵住二进制文件静默入库（素材库乱码）

### 问题

浏览器上传走 `FileReader.readAsText`，PDF/DOCX/XLSX 这类二进制文件到了服务端就是一堆乱码文本；而 `parseMaterialContent` 对 `pdf`/`word` 格式**只要来的是文本就标记 `status: ready` 入库**，从不判断「是否真的解析出了正文」。结果是乱码被当成正常素材存下来，且 `error` 为 `null`，看不出有问题。

（`excel` 格式同一类问题：乱码里大概率含逗号，会被 CSV 分支当成 `ready`。）

### 改动

- `server/validation.mjs`：新增 `binaryUploadError()`，在 `parseMaterialContent` 入口对所有文本类格式统一拦截，判据用实测过的信号——压缩包魔数（PK 紧跟 0x03 0x04）、PDF 文件头、NUL 字节、UTF-8 解码乱码字符占比。命中时返回 `status: failed` 并给出可执行的原因（「请另存为 .txt 或 .md 后重新上传」），`content` 仍保留原文便于排查与重试。
- `src/main.tsx`：上传前先按扩展名拦一层，直接给提示，不再产生垃圾素材记录。
- 浏览器文本解码出少量坏字符不会被误伤：实测正常中文正文乱码占比 0%，含 3 个坏字节的文本 0.7%，而真实二进制 42%–44%，阈值取 5% 有足够余量。

### 验证

- 192→193 项测试全绿（新增 2 项：二进制拦截、正常文本不误伤），`tsc --noEmit`、生产构建通过。
- 重启本地 API 后用真实接口上传四种文件核对：假 DOCX、假 XLSX、假 PDF 全部 `status: failed` 并给出对应原因，正常 Markdown 仍为 `ready`。
- 顺带扫描了他素材库里已有的素材：37 条中带二进制乱码特征的只有本次验证产生的 3 条（验证后已软删除），**他原有素材没有被这个 bug 污染**。

### 未做

- 没有引入文档解析依赖，所以 DOCX/PDF 仍然只支持「先另存为文本」。要真正支持二进制解析，需要新增依赖（mammoth/PDF 解析库），这是独立决定，没有擅自加。
- 受浏览器上传限制，PDF/DOCX 的真实解析仍走桌面同步通道（`parseSyncJob` 有 buffer 路径，DOCX 会诚实报「需要文档解析依赖」）。

### 4. 体验闭环（对标 Easel 五层工作流补缺）
