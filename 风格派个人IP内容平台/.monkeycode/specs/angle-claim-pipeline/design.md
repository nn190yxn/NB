# Design: 角度—主张—成稿链路

Feature Name: angle-claim-pipeline
Updated: 2026-09-21

链路本身：`ComposePanel`（`src/main.tsx:1470–1535`）发出的生成请求只有 `{ topic_id, structure_id?, content_format?, quote_ids, experience_ids }`，**没有 `material_ids`**。全前端 `material_ids` 只出现在 `main.tsx:1881` 的选题生成。「确认做」（`:1893`）直接零素材生成。后端 `buildDraftBrief` 的 `material_roles` 与 `material_gap` 因此永远走空路径，模型只拿到标题。

## 二、数据模型改动

**materials**
- `+ angle: string`（建议九项词表，可自由填；空值可读）
- `+ claims_run: string`（同一次「提主张」的两组主张共享此标识，用于确定正反配对）
- `+ logic_status: 'unchecked' | 'passed' | 'conditional' | 'failed'`
- `+ logic_note: string`（断点说明，指得到原文）
- `+ logic_checked_at: string` + 判定时正文身份快照，正文一改即退回 `unchecked`
- `checksum` 一律改为「归一化正文」的哈希，不再掺来源编号
- 四档结论**都不构成拦截**：`failed` 的主张照常进简报，只在界面标灰与显示断点

**topics**
- `+ angle: string`
- `+ viewpoint_material_id: number | null`（主观点，指向一条主张素材）
- 反方不需要新字段：从主观点素材的 `claims_run` 加"角度不同"就能查出同一次拆解的对立那组
- 沿用 `strategy_layer`、`hook_kind` 的既有做法：用户点名即以人为准，模型不折中

**research**
- 字段不变，`persistResearch` 改为按 `(owner, platform, title)` 命中即保留原编号

**不新增表、不新增子系统。** 角度、主观点、配对标识都是标量字段；反方靠"同一次运行的配对标识 + 角度不同"查出来，不建关系表、不建聊天室引擎。

## 三、关键决策与理由

### D1 角度用字段表达，不做多角色聊天室

`dbs-chatroom` 那种一次跑出多个专家对话的引擎能出好素材，但它是一个新模块：多轮提示词、发言人一致性、成本不可控。而"市场/管理/经营/人"这些角度根本不是角色，用角色对话器表达反而别扭。

字段方案：一次「提主张」= **一对成对比的角度**（用户 2026-09-21 定：老板 / 员工、经营 / 市场这类）。两组主张带同一次运行的配对标识，于是"反方"是确定的配对而不是事后猜测。要更多角度就再点一次；整张词表批量跑留给链路跑通之后。代价是一次调用输出翻倍、提示词要守两个角度不串味；收益是每一步单独可查、失败只重跑一对。

建议词表九个：市场 / 经营 / 管理 / 财务 / 老板 / 员工 / 客户 / 同行 / 平台。只是建议，用户能填任何词，不做枚举校验——做成死选项，它就变成了我们自己发明的分类。

### D2 逻辑判定放在主张层，且**只标不拦**

用户的位置是对的：判定该作用在主张上，不是作用在被模型圆过的成稿上（同文同提示词 6 次只有 3 次抓到问题，这条记录在 `main.tsx:926` 的文案里；稿子阶段它还来得及把断处写顺）。

原方案让"不成立"默认不进简报。用户在 2026-09-21 否掉了：逻辑不成立的主张，它的**利观点**可能还能用。所以现在判定**没有否决权**——不成立的照常进简报，界面上标灰并显示断在哪一处，用户自己决定踢掉还是照常用。

这样做的理由：判定由模型给，不稳的东西不配当闸门；但它给的**断点说明**当场就能看，价值全在这里。两道关口（主张层、稿子层）于是都只做标注，拦停权只留给客观可判定的那几条。

### D3 素材身份只看归一化正文，来源退化成引用

现在的五套编码把"从哪来"掺进了"是什么"，所以同一句话从两个门进来必然不等。归一化函数已有实现（`return-flow.mjs:24`，去空白与中英标点），本特性只是把它提出来共用，不新写一套。

代价：同一句话被不同来源引用时只剩一条，来源列表变长。这是**期望行为**——用户问的从来是"这句话我收过没有"，不是"这句话我从哪个门收的"。

风险与护栏：文本归一化相同但 `material_kind`/`unit_type` 不同（一句话既是金句又被当判断），不自动改判，只提示用户定一个。宁可让人判一次，不让机器猜。

### D4 主观点是一条主张素材，不是选题上的新文本框

另一种做法是给选题加一个自由文本 `viewpoint`。被否决：那样观点是稿子的附件，不复用、不可判逻辑、不可溯源，和素材库两套。指向素材库里一条 OPI，则 Requirement 7 的逻辑判定天然作用在观点上，且"我认可这个热点当观点"与"我自己写一条观点"是同一个动作。

代价：观点必须先存在于素材库。这是好事——它保证库里每条被用出去的观点都有出处。

### D5 「驳」用真实反方

生成提示词现在有一句「主体先驳后立：先点破常见做法」，但没有任何输入告诉模型"常见做法"是什么，于是它编。一次提主张跑出来的一对角度，正是现成的、真实的对立面：立老板角度的观点时，员工那组主张就是被驳的对象。这不新增引擎，只填已有格子里空着的一格。

### D6 先做版本可见，再动业务

不是洁癖：后台进程 22 小时未重启、36 个 commit 未生效，意味着此前所有"测了说不行"都可能测的是旧代码。不做这条，本特性每一批的验收都不可信。成本约几十行。

## 四、必须同批更新的既有测试断言

## 五、接口清单

**新增**
- `POST /api/topics`（标题、角度、主观点、层级、钩子；来源引用可选）
- `GET /api/materials/duplicates`（按归一化身份分组，只返回有成组的）
- `POST /api/skills/claims/check`（对一条主张判逻辑，三档 + 断点）
- `/api/version`（代码标识与启动时间）

**扩展**
- `PATCH /api/materials/:id` 放开 `content`、`name`、`material_kind`、`unit_type`、`angle`；改正文时重算身份，冲突返回 409
- 「提主张」接受**一对**角度参数，产出两组逐条主张，两组带同一配对标识
- `POST /api/drafts/generate` 接受 `material_ids`（后端已支持，只是没人传）
- `PUT /api/topics/:id/revision` 允许改角度与主观点

**保持不动**：`buildDraftBrief` 的分组与稳定排序、`material_trust` 三档、派生素材不入案例位、四道稿子检查、平台基座与字数目标、形式判断、配额与加密配置、账号隔离、MySQL 迁移。
