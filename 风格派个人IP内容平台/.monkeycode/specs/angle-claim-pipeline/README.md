# 角度—主张—成稿链路（angle-claim-pipeline）

作者：Qoder
日期：2026-09-21
状态：**书面规格，代码未动。等用户回答第 5 节五个决策点后开始批次 0。**

## 简介

用户的产品模型是六块：① IP 定位与流量配比 → ② 素材库 → ③ 主题按角度拆解成立场与主张 → ④ 逐条判逻辑，成立才成文 → ⑤ 装备式改写（标题 / 开头 / 正文格式 / 结尾 / 手写）→ ⑥ 去 AI 化、人工终审、拍摄发布、数据回流。

实测对照下来：**①⑤⑥ 是通的**，**② 在做但重叠且清不掉**，**③ 缺「角度」这个维度**，**④ 的检查对象放错了**（查成稿，不查主张）。③④ 两处断掉导致成稿那一步只收到一个标题，模型没有料可写，只能编案例和数字——这是「整体逻辑实现困难」的真正卡点，不是模型能力问题。

本特性做四件事：

1. **先让「修好了」可被证明。** 当前端口 3001 的后台进程启动于 2026-09-20 01:15，此后 `server/`＋`src/` 提交了 36 个 commit 而未重启，前端 Vite 会热更新、后台不会。今天白天所有「测了说不行」的结论都建立在 22 小时前的代码上。
2. **素材身份收敛成一套**，并把删除 / 编辑 / 合并的能力还给用户。
3. **「角度」提升为一等字段**：一个主题按多个角度拆，每个角度得到自己的主张，每个角度立一条选题、出一篇稿。
4. **逻辑判定前移到每条主张上**，作为进料门槛而不是事后提醒；同时把已有但从未接通的「按认知角色进料」那条线接上。

## 核心结论（三条）

1. **③④ 断点的性质是接线，不是缺功能。** 后端 `buildDraftBrief` 的五角色分组、`material_gap` 裸写声明、派生素材不进案例位，代码全在、测试全绿；前端 `ComposePanel` 发出的请求根本没有 `material_ids` 这一项，格子永远是空的。
2. **逻辑检查放在成稿上做不到它想要的事。** 稿子阶段模型会把有问题的主张圆通；而且同文同提示词跑 6 次只有 3 次抓到问题（记录在 `src/main.tsx:926` 的状态文案里）。放到主张上，一次判定成本低、结论当场可见。
3. **三处测试把当前的错误行为当正确锁住了**：`server/web-assets.test.mjs:237` 死锁了缺 `material_ids` 的请求字面量，`server/claims.test.mjs:46,55` 要求「确认后恰好新增一条」，`server/materials-atoms.test.mjs:66` 要求「原文完全相同才去重」。不显式改这三条，第 2、3 批一步都动不了。规格与测试必须同一批改，不留互相矛盾。

## 规模

6 个批次、**46 个任务**（明细见 `tasklist.md`）。M1 = 批次 1 完（18 项），M2 = 批次 3 完（36 项，端到端跑通一次），M3 = 全部完（46 项）。

用户 2026-09-21 已拍板五处口径，全部记在 `decisions.md`，其中三处推翻了我的默认：主张逻辑判定**只标不拦**（逻辑不通但利观点可用）、一次提主张跑**一对角度**（老板/员工、经营/市场）、重复素材**自动合并**不逐组确认。语言层「不设条数上限」维持现状。

## 本特性不做什么

不建多立场聊天室引擎（角度用字段表达，不用新模块）；不改账号隔离、AES 密钥存储、MySQL 迁移；不扩平台（继续抖音 + 视频号）；不动字数目标与形式判断；不把语言层检测器当本特性的阻塞项（单列批次 5，需单独批准）。
