# Decisions: 拍板记录

Feature Name: angle-claim-pipeline
Updated: 2026-09-21

五个决策点已由用户在 2026-09-21 全部回答。以下是生效口径，`requirements.md` 与 `design.md` 已按此改过。

## Q1 逻辑判定不通过的主张 → **默认进简报，只标不拦**

用户原话：不成立也可以默认进，也可以让我手动放行。因为逻辑可能不成立，但它的**利观点**（利益立场）可能还可以。

采纳口径：主张逻辑判定**没有否决权**。`logic_status === 'failed'` 的主张照常进简报，界面上标灰并显示断在哪一处，用户随时能把它踢出本题素材。

这条推翻了我原本的默认（不成立默认不进）。连带效果：Requirement 7 从"进料门槛"降级成"进料标注"，逻辑判定的价值全部落在**当场可见的断点说明**上，而不是拦。稿子层面的四道检查也保持原样，两道都不拦稿。

## Q2 角度建议词表 → 九个，含老板与员工

`市场 / 经营 / 管理 / 财务 / 老板 / 员工 / 客户 / 同行 / 平台`

仍只是建议，用户能填任何词。原草案里的「人（员工·顾客）」被拆成老板 / 员工 / 客户三个，不再单列。

## Q3 一次提主张 → **跑两个成对比的角度**

用户原话：可以变成两个对比的角度，比如老板和员工、经营或者市场。

采纳口径：一次「提主张」调用传入一对角度，产出两组主张，两组之间天然是正反关系。这条让 Requirement 10 的"反方"从"事后按同源性去猜"变成"同一次拆解的确定配对"——配对关系记在素材上，选题默认取对立那组作反方。

代价：一次调用的输出翻倍，提示词要同时守两个角度不串味。仍然一次一对，不做整张词表批量。

## Q4 重复素材 → **自动合并**

用户原话：人工确认不行，改成自动合并。

采纳口径：合并脚本自动完成——同文归一后保留最早一条、来源引用合并、其余软删。合并前把 `data.json` 备份到 `backups/`，并产出一份"谁并进了谁"的清单；被归档的素材保留原记录，能恢复。

界面仍保留 Requirement 3 的分组视图与「疑似重复」入口，但那是**查看**和事后修正，不是合并的前置条件。

## Q5 语言层不设条数上限 → **保留现状**

用户原话：不是不设上限，我觉得没问题，最多需要多少条以后再看。

`server/draft-checks.mjs:620` 的「不设条数上限」维持不动，批次 5 撤掉这一项。它与早期「一次一条、上限 7 条」的口径冲突由此判定为**以代码现状为准**，旧口径作废，不再留成悬案。
